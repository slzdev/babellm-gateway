# Forced upstream streaming

Date: 2026-08-18
Status: designed, to be implemented on `worktree-force-upstream-stream`

## Problem

Anthropic refuses a non-streaming request whose model and token budget put it
over a ten-minute ceiling, before generating anything:

```json
{"error":{"message":"Streaming is required for operations that may take longer
than 10 minutes. See https://github.com/anthropics/anthropic-sdk-typescript
#long-requests for more details","type":"api_error","param":null,
"code":"upstream_error"}}
```

The gateway forwards the client's `stream` verbatim, so a client that sends
`stream: false` gets that refusal even though the gateway is perfectly capable
of streaming upstream and handing back a single body. Other providers have the
same ceiling under other names, and OpenAI-shaped clones in front of long
reasoning models are heading the same way.

The client's `stream` is the wrong thing to be deciding the upstream call. It
says what the *client* wants to receive; whether the *upstream* leg is streamed
is a property of the endpoint being called, which is an operator's fact.

## Decision

A new setting, `force_upstream_stream`, settable per provider and overridable
per catalog model. When it is on and the client did **not** ask for streaming,
the gateway opens a streaming request upstream, drains it, collapses the result
into a single non-streamed body, and answers the client exactly as it does
today. When the client *did* ask for streaming the setting is inert — the
request is already streamed end to end.

It applies to both ingresses (`/v1/chat/completions` and `/v1/responses`) and
to every adapter, because it is about the upstream call rather than the
dialect.

Separately, `DEFAULT_TIMEOUT_MS` drops from 120 s to 30 s and the previously
hidden `config.timeoutMs` becomes an editable field, so an operator can raise
the ceiling on the providers that serve long requests. Without that, a request
forced to stream in order to survive ten minutes would still be killed by the
gateway's own two-minute cap.

## 1. Data model

```
providers.force_upstream_stream       boolean NOT NULL DEFAULT false
catalog_models.force_upstream_stream  boolean            -- NULL = inherit
```

Both are **columns**, not catalog layers, for the reason already written above
`catalog_models.apiFlavor` in `src/lib/db/schema.ts`: `sync()` and `merge()`
must never touch them, so a re-sync cannot undo an operator's decision and a
model that goes missing keeps the setting for when it comes back. The comment
on the existing column block is extended to cover the new one rather than a
second one being written beside it.

The catalog column is genuinely tri-state:

| value   | meaning                              |
|---------|--------------------------------------|
| `NULL`  | inherit the provider                 |
| `true`  | force, whatever the provider says    |
| `false` | never force, whatever the provider says |

`false` is not the same as `NULL`, which is why the column is nullable with no
default — the same distinction `route_targets.breaker_threshold` documents.

Migration `0010`, generated by `drizzle-kit generate`. Two `ADD COLUMN`s, no
enum change, so nothing needs splitting across transactions.

## 2. Resolution

`Candidate` in `src/lib/gateway/resolve.ts` gains:

```ts
  /** Whether to open the upstream leg as a stream even when the client asked
   *  for a single body. Resolved rather than nullable, for the same reason
   *  `apiFlavor` is: the routing loop must never have to work out where the
   *  answer came from. */
  forceUpstreamStream: boolean
```

Resolved identically in both `findVirtualModel` and `resolveDirect`, on the
line below `apiFlavor`:

```ts
forceUpstreamStream: catalog?.forceUpstreamStream ?? provider.forceUpstreamStream,
```

`??` and not `||`, because `false` on the model must beat `true` on the
provider.

### `createAdapter`'s signature

Adding a fifth positional argument to

```ts
createAdapter(provider, flavor, paths, maxOutputTokens)
```

would leave four consecutive optional values at the call site with nothing but
their order to tell them apart. The four are all the same kind of thing —
what resolution worked out about one target — so they become one object:

```ts
/** What resolution worked out about one target, as opposed to what the
 *  provider is. Every field is optional so a caller with no model in hand —
 *  catalog sync, the provider test button — can omit the lot. */
export interface TargetSettings {
  flavor?: ApiFlavor
  paths?: ModelPathOverrides | null
  maxOutputTokens?: number | null
  forceStream?: boolean
}

export function createAdapter(
  provider: ProviderRow,
  settings: TargetSettings = {},
): ProviderAdapter
```

`flavor` continues to default to `provider.apiFlavor` and `forceStream` to
`provider.forceUpstreamStream` when the key is absent, so `createAdapter(row)`
in `src/lib/catalog/sync.ts` and `src/lib/admin/providers.ts` keeps working
unchanged. `ExecuteDeps.createAdapter` and `GatewayDeps.createAdapter` narrow
to the same two-argument shape, and `execute.ts` passes one object built from
the candidate.

This rewrites roughly twenty call sites in `tests/lib/adapters/registry.test.ts`
and the `toHaveBeenCalledWith` assertion in `tests/lib/gateway/execute.test.ts`.
That churn is mechanical and is the price of the fifth setting not being the
one that makes the signature unreadable.

## 3. The mechanism

Two new pure functions in `src/lib/adapters/collapse.ts`, a sibling of
`wrappers.ts` and imported by nothing else:

```ts
collapseChatStream(chunks: AsyncIterable<ChatCompletionChunk>): Promise<ChatCompletion>
collapseResponseStream(events: AsyncIterable<ResponseStreamEvent>): Promise<ResponsesResult>
```

and two wrappers beside `withRespondViaChat` in `src/lib/adapters/wrappers.ts`:

```ts
export function withForcedChatStream<T extends ChatOnlyAdapter>(adapter: T): T
export function withForcedResponseStream(adapter: ProviderAdapter): ProviderAdapter
```

Each returns a spread of its argument with one method replaced, so the generic
on the first one keeps a full `ProviderAdapter` a full `ProviderAdapter`.

`flavoredAdapter` in `registry.ts` is the only place that composes them:

```ts
function flavoredAdapter(
  runtime: ProviderRuntime,
  flavor: ApiFlavor,
  maxOutputTokens: number | null,
  forceStream: boolean,
): ProviderAdapter {
  if (flavor === 'responses') {
    const base = createResponsesAdapter(runtime)
    // Both native pairs, wrapped independently: a Responses request must not
    // round-trip through chat shape just because chat is being forced too.
    return forceStream ? withForcedResponseStream(withForcedChatStream(base)) : base
  }
  const base = flavor === 'anthropic_messages'
    ? createAnthropicAdapter(runtime, maxOutputTokens)
    : createOpenAIAdapter(runtime)
  return withRespondViaChat(forceStream ? withForcedChatStream(base) : base, runtime.name)
}
```

Gemini takes the same treatment in `createAdapter`'s `case 'gemini'`.

For a chat-only adapter the wrapper goes **inside** `withRespondViaChat`, so
`respond` derives from the already-forced `chat` and one wrapper covers both
ingresses. That ordering matters and gets a comment.

`handler.ts`, `execute.ts`, both `Ingress` implementations, and all four
adapters are untouched.

### Why this is safe for failover

`chat()` now drains the whole upstream stream before resolving. A mid-stream
upstream failure therefore surfaces as an ordinary rejected promise *before*
the gateway has committed an HTTP response, so `execute()`'s chain sees it and
fails over — which is strictly better than today, where the same failure on a
non-streaming call is a single opaque error. The streaming client path is
unchanged and keeps its existing first-chunk failover boundary.

The one cost is latency to first byte for the client, which is unchanged in
substance: a non-streaming client waits for the complete answer either way.

## 4. What `collapseChatStream` preserves

Choices are accumulated into a map keyed by `choices[].index` and emitted in
index order, so `n > 1` survives.

Per choice:

- `delta.role` — first non-empty wins; defaults to `'assistant'`.
- `delta.content` — concatenated. Absent throughout means `null`, not `''`:
  a tool-call-only completion has no content, and `''` would misreport it.
- `delta.refusal` — concatenated, same rule.
- `delta.reasoning_content` — concatenated onto `message.reasoning_content`.
  Non-standard, but load-bearing: all three translate modules emit it on both
  their unary and stream paths (`chat-to-anthropic.ts:324,425` and its two
  siblings), `protocols/chat.ts` reads it in `isContentDelta`, and
  `responses-to-chat.ts:370` reads `message.reasoning_content` off the **unary**
  completion to rebuild a reasoning item. Dropping it in the collapser would
  therefore lose reasoning outright on a Responses request served by a forced
  Anthropic target — the exact combination this feature exists for.
- `delta.tool_calls` — merged by each entry's own `index`, which is a
  different index from the choice's. `id`, `type` and `function.name` arrive
  once and are taken as they come; `function.arguments` concatenates.
- `finish_reason` — last non-null wins.
- `logprobs` — `content` and `refusal` arrays concatenate; `null` when no
  chunk carried any.

Top level: `id`, `model`, `created`, `system_fingerprint` and `service_tier`
come from the first chunk; `object` is `'chat.completion'`; `usage` is
whichever chunk carried one last, and `undefined` when none did —
`chatStream` already asks for `stream_options.include_usage` unless the
provider sets `disableStreamUsage`. Accepted, but not free: on a provider that
sets that flag, forcing *removes* usage from a request that had it. Unforced,
a `stream: false` request reads usage off the non-streaming body, which never
involved `stream_options` at all — so the request is served and logged with no
tokens, no cost, and no contribution to the key's tpm or spend counters.
Re-enabling `include_usage` here would defeat the flag, so the answer is not
to force a provider that sets it; the README says so beside the feature.

A stream that yields **zero** chunks throws rather than returning an empty
completion, so the chain fails over. The throw is a plain `Error`;
`classifyProviderError` turns it into a retryable 502, which is the honest
reading of "the upstream opened a stream and said nothing".

Chunks are consumed with `for await`, so the adapter's own `try/catch` around
its iteration still classifies upstream failures before they reach here.

## 5. What `collapseResponseStream` preserves

Everything, without reconstruction. Every terminal event on the Responses
stream — `response.completed`, `response.incomplete`, `response.failed` —
carries the full `Response` object, so the collapser iterates until it sees one
and returns `event.response` verbatim.

`response.failed` **returns** rather than throws: a real non-streaming
`responses.create` answers HTTP 200 with `status: "failed"` and an `error`
field, and the collapsed path must be indistinguishable from it.

A stream that ends with no terminal event throws, for the same reason and with
the same classification as the empty chat stream.

## 6. Timeout

`DEFAULT_TIMEOUT_MS` in `src/lib/gateway/execute.ts` drops from `120_000` to
`30_000`.

**This changes behaviour for every existing provider**, not only forced ones:
anything that currently takes between 30 s and 120 s starts failing over where
it used to succeed, until an explicit timeout is set on it. That is deliberate
— a 30 s ceiling with a visible override is a better default than a hidden
120 s one — and it is called out in the README under a `> [!WARNING]`.

`config.timeoutMs` becomes editable in both provider dialogs as **Request
timeout (ms)**, placeholdered `30000`. It is merged onto the stored config
exactly as `registryNamespace` already is in
`src/app/(admin)/providers/actions.ts`, and the key is deleted when the field
is blank so blank keeps meaning "the default" rather than pinning 30000
forever. Validated as an integer in `1…3_600_000`; anything else is a form
error, not a silently ignored value.

## 7. Admin surface

**Provider dialogs** (`provider-form.tsx`, `edit-provider-form.tsx`) gain a
**Force upstream streaming** control and the timeout field. The switch is
rendered for every adapter, because the setting is about the upstream call and
not the dialect — unlike the API-flavor selector next to it, which stays
hidden for `gemini` and `bedrock`.

The shadcn `Switch` in `src/components/ui/switch.tsx` is the preferred
control per `AGENTS.md`. It must be verified to submit through `FormData`
under a `name`; if the underlying Base UI primitive renders no form control,
the fallback is a plain `<input type="checkbox">` matching the neighbouring
`useInstanceRole` field rather than a hidden-input workaround.

Copy:

> Open the upstream request as a stream even when the client asked for a single
> response. Some providers refuse long non-streaming requests. The client still
> gets one response — only the upstream leg changes. Default for every model on
> this provider; override it per model on the Catalog page.

**Catalog gateway dialog** (`catalog-forms.tsx`) gains a tri-state selector
from a new `src/components/admin/force-stream-select.tsx`, modelled directly on
`api-flavor-select.tsx` — same file location and same reasoning, since the
provider dialogs are client components and cannot import server-only modules.
Its blank option reads `(inherit — forced)` or `(inherit — not forced)` so the
inherited value is visible without opening the Providers page, and its two
explicit options are `Force` and `Never force`.

**Types.** `ProviderListItem` and `ProviderInput` in `src/lib/admin/providers.ts`
gain `forceUpstreamStream`, and the list item also surfaces the resolved
`timeoutMs` for the edit dialog to prefill. `CatalogListItem` gains
`forceUpstreamStream: boolean | null` and `providerForceUpstreamStream: boolean`
beside the existing `providerApiFlavor`. `ModelGatewayInput` gains
`forceUpstreamStream?: boolean | null` under the same discipline its existing
comment states: `undefined` leaves the field alone, `null` is a value meaning
"inherit".

No response header and no request-log field: a forced request is indistinguishable
on the wire from an unforced one, by decision.

## 8. Testing

New `tests/lib/adapters/collapse.test.ts` carries most of the weight, against
hand-built async iterables and the two existing fixtures:

- plain text across several chunks, including a chunk with an empty delta
- `tests/fixtures/openai-tool-call-stream.json` — one tool call reassembled,
  arguments concatenated, `finish_reason: 'tool_calls'`
- two tool calls interleaved by `index`
- `reasoning_content` accumulated separately from `content`
- content absent throughout collapses to `null`, not `''`
- `n > 1`: two choices emitted in index order
- usage taken from the final chunk; absent usage stays `undefined`
- empty stream throws
- `tests/fixtures/openai-responses-tool-call-stream.json` — the Responses
  collapser returns the terminal event's response verbatim
- a Responses stream ending in `response.failed` returns rather than throws
- a Responses stream with no terminal event throws

`tests/lib/gateway/resolve.test.ts` gains the inheritance matrix: model `NULL`
takes the provider's value in both directions, model `false` beats provider
`true`, and both hold for a direct `provider/model` address as well as a
virtual model.

`tests/lib/adapters/registry.test.ts` gains composition tests — a forced
chat-only provider produces an adapter whose `chat` reaches the streaming
endpoint, a forced `responses` provider does so on both `chat` and `respond`,
and an unforced one is byte-for-byte the adapter built today — plus the
signature rewrite across its existing cases.

New `tests/gateway/forced-stream.test.ts` covers the end-to-end contract
through `runGatewayRequest`: a client `stream: false` against a forced target
receives a single JSON body while the upstream saw `stream: true`; the same
request against an unforced target still calls the non-streaming method; a
client `stream: true` is unaffected either way; and an upstream that fails
partway through a forced stream fails over to the next target, which is the
behaviour that would silently regress if the wrapper were ever moved outside
`execute()`.

`tests/lib/gateway/execute.test.ts` gains a case pinning the 30 s default and
one pinning that `config.timeoutMs` overrides it, and
`tests/lib/admin/providers.test.ts` gains the timeout field's validation
bounds.

## Out of scope

- **Per-route-target forcing.** `route_targets` already carries `service_tier`
  and the breaker overrides, so a third level is expressible, but nothing yet
  needs the same catalog model forced on one virtual model and not another.
- **Forcing the other direction** — de-streaming a client's `stream: true`
  into a non-streaming upstream call. It has no failure it would fix.
- **Honouring `catalog_models.supports_streaming`.** An operator turning the
  setting on for a model the catalog believes cannot stream is making an
  explicit decision, and the catalog's streaming flag is frequently absent or
  wrong for `openai_compatible` clones. Silently ignoring the setting would be
  worse than letting the upstream reject the request.
- **A global default in the `settings` table.** `api_flavor` has none either;
  the provider level is already the "set it once" level.
